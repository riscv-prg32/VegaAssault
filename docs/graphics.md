# Graphics and Sprite Pipeline

Sprites use one-byte palette indices into a 14-entry RGB565 palette. A fixed 48x24 RGB565 scratch buffer is decoded before each draw. RGB565 stores red in five bits, green in six, and blue in five, giving a 16-bit pixel representation well suited to embedded displays. A designated value is used for transparency. Terrain and backgrounds are preferentially generated with primitives rather than full-screen bitmaps, preserving cartridge space.

`tools/generate_assets.py` is the authoritative art generator. It produces `src/sprites.c`, `src/sprites.h`, and `assets/sprite-sheet.png`. Generated arrays are derived artifacts: pedagogical modifications should normally begin in the generator, then regenerate and verify the outputs.

This pipeline illustrates a general systems principle: expensive authoring representations can be transformed offline into simple runtime representations. The microcontroller spends cycles drawing pixels rather than parsing image formats.

## 2026 pixel-art redesign

The current art pass uses classic cel-animation conventions: dark ink contours, stepped metallic highlights, tapered armor plates, recessed eyes, and articulated gauntlets. The player has a project-specific split crest, cheek fins and divided breastplate; docking uses swept segmented wings. Enemies retain blade, crawler, horned-beast and gunner roles, while bosses now have winged, carapaced and siege silhouettes. These are project design choices, not PRG32 requirements or reproductions of character model sheets.

All 24 frames retain their 16x16, 24x24, 32x24 and 48x24 envelopes ; the four former `transform_*` names are now `double_spazer`, `marine_spazer`, `drill_spazer`, and `all_spazers`. Storage remains 15,232 bytes of indices, a 28-byte palette and a 2,304-byte decode buffer. The 14-color palette uses muted armor tones and bright eyes/reactors; only `0xffff` is transparent. Animation changes limb positions, tread pixels, exhaust or reactor illumination. Docking now moves Grendizer onto the selected support craft; Special Cosmo combines the three support craft without a robot; Grendizer has manually selected robot and combined forms, with the detached craft rendered independently.

Every runtime pixel is generated locally by `tools/generate_assets.py`. Integer polygon fills and ink contours are rasterized offline with Pillow, with no new runtime graphics calls or memory requirements. The Store icon and splash use the same generator. Regenerate the sprite sheet and native gameplay preview after art edits.

## Decode contract

Palette storage is a project design decision. The inspected PRG32 `prg32_sprite_draw_frame` implementation synchronously consumes RGB565 pixels before returning; that observed behavior permits buffer reuse. `sprite_draw` accepts only generated frames up to 48x24 and performs O(width × height) integer lookups without allocation. White (`0xffff`) remains transparent. The original palette-index conversion preserved the decoded artwork; subsequent art passes intentionally change the generated pixels. The extra decode pass needs frame-time verification on each host.

## Gameplay capture

The native preview `assets/gameplay.png` is generated by `python3 tools/capture_screen.py` (host C compiler, Pillow, and the configured PRG32 checkout required). `PRG32_ROOT` defaults to the sibling framework checkout. The capture compiles the actual cartridge alongside PRG32's software rectangle, text, font and sprite rendering functions, extracted into a temporary header. Input, graphics locking and audio services are replaced by a deterministic input script, single-threaded no-op locks and silent audio stubs. No gameplay positions or entities are injected.

`tests/capture_game.c` runs 292 update/draw ticks: START at ticks 0 and 2 enters the game, and A is held from tick 260. It asserts live first-stage gameplay, exports the 320×200 RGB565 viewport as RGB888, and the Python driver enlarges it to 960×600 using nearest-neighbor sampling. Host-band cropping and integer enlargement are the only presentation changes. This is a real game-code render, not an illustration or a QEMU/ESP32 execution claim. The capture is compiled with C99 warnings-as-errors and address/undefined-behavior sanitizers. The PNG depends on the game source, upstream renderer/font, and Pillow version; regenerate it after relevant visual changes.

The README now shows `assets/qemu-gameplay.png`, captured from the actual ESP32-C3 QEMU host; see [QEMU validation](qemu.md#observed-validation). The native preview and capture script remain available independently.

## Campaign visual fixtures

`python3 tools/capture_campaign.py` generates `assets/campaign-scenes.png` using the actual game renderer under sanitizers. Twenty labeled fixtures explicitly select launch timings, all five playable stages, the Moon base boss, victory and all four docking screens. This differs from the input-only gameplay capture: fixture state is injected for visual QA and is not evidence of a completed playthrough. Original Double, Marine, Drill and combined sprites occupy the old docking slots, using 15232 index bytes, 28 palette bytes and the 2304-byte decode buffer. Mountain/waterfall doors, clouds, water, tunnel, lunar terrain, base towers and burning ruins use constant-memory procedural geometry.

The unused `grendizer_2` pose is replaced by the generated 32×24 `solo_spazer` (192 additional index bytes). Open blue sky and separate clouds make Double's environment unambiguous; Marine uses water/bubbles, and Drill uses a dark rock cavity enclosed by ceiling/stalactites and floor. Assembly, launch, lunar forms and epilogue snapshots are included in the campaign fixture sheet.

The current video and scene fixtures use DOWN+A / UP+A to select lunar robot/combined form. The former automatic form clock has been removed. The controls legend now displays these transformation chords in every combat stage. No sprite data or decode-buffer capacity changed in this revision.
